# SPC 위반 사건 단위 묶기 — 설계 (짧은 설계)

## 왜

같은 이상 하나에 넬슨룰 여러 개가 동시에 성립하면 룰마다 위반이 한 줄씩 쌓인다.
(사출기 3호 금형 온도: 실제 상황 3개 → 위반 9건)

- 실무자가 같은 일을 여러 번 확인하고, 경보가 실제보다 많아 보인다 (경보 피로).
- 원인 점수 (a) 가 "위반 룰 종류 수"를 세므로 이상 하나가 룰 3개만 걸려도 만점이 된다 (중복 계산).

## 목표 / 비목표

- 목표: 같은 특성 · 같은 방향 · 가까운 시각의 위반을 사건 1건으로 묶고, 걸린 룰은 사건의 라벨로 보여준다.
  사건 단위로 확인(ack)하고, 원인 점수 (a) 는 사건 단위로 센다.
- 비목표: 룰 판정 로직(넬슨룰 8종, 파라미터, 관리도 점 표시) 변경, EWMA 등 새 탐지기.
- 반목표: 탐지 시점이 늦어지거나 이상을 놓치게 되는 변경.

## 방식 (사용자 선택: A)

| | A. 읽을 때 묶기 (선택) | B. 사건 테이블 추가 |
|---|---|---|
| 저장 | 위반은 지금처럼 룰별 저장, 조회·점수 계산 때 순수 함수로 묶음 | 새 테이블 + 재계산마다 연결 |
| DB 변경 | 없음 (위반 points JSON 에 z 값만 추가) | 마이그레이션 |
| 단점 | 사건 고유 번호 없음 → 가장 작은 위반 번호를 사건 번호로 | 재계산 때 사건 재분할·확인 상태 이전 로직 |

A 선택 이유: 위반이 그대로 원본으로 남아 되돌리기 쉽고, 묶는 기준을 바꿔도 과거 데이터를 고칠 필요가 없다.

## 묶는 규칙 (`app/core/spc/events.py`, 순수 함수)

- 특성별로 위반을 경보 시각(신호 점) 순으로 보며, 직전 사건에 붙일지 새 사건을 열지 정한다.
- 방향: R1·R2·R5·R6 은 포함 점 z 합의 부호(위/아래), R3 은 값의 추세 방향, R4·R7·R8 은 양쪽(0).
- 방향 있는 위반: 직전 사건과 방향이 같거나 직전 사건이 양쪽이고, 포함 점이 직전 사건의 마지막 점 + gap 이내에서
  시작하면 붙인다 (창이 긴 R2 가 같은 방향 사건에 붙도록 겹침 허용).
- 양쪽 위반(R4·R7·R8): 신호 점이 직전 사건 마지막 점 + gap 이내일 때만 붙인다 (긴 창이 사건 사이를 잇지 않게).
- gap 기본 3점, 설정 `control_chart.event_gap_points`.
- 사건 시각 = 가장 이른 신호 시각, 확인 상태 = 모든 위반이 확인됨. 일부만 확인이면 "새 룰 추가, 미확인".

## 바뀌는 곳

- API: `GET /spc/events`, `POST /spc/events/ack {violation_ids}` (사건 안 미확인 위반 전부 확인, 감사 로그는 위반별),
  `/spc/characteristics` 에 `open_events`, 관리도 payload 에 `events`. 기존 위반 API 는 유지.
- 원인 점수 (a): 경로상 LOT 에 걸린 사건 수 / `cause_scoring.spc_event_saturation`(기본 2).
  여러 특성에 걸친 이상이 룰 여러 개보다 강한 근거라는 판단 (내 결정).
- 어시스턴트 도구 `get_spc_violations`: 사건 목록으로 반환 (이름 유지).
- 화면: 대시보드 "미확인 SPC 사건" 카드·목록 + 확인 버튼(실무자 이상), 관리도의 위반 목록 → 사건 목록,
  특성 목록의 미확인 수 → 사건 수. 관리도 점의 룰 표시는 그대로.
- 그대로 두는 곳: 실시간 시연의 경보 알림과 3D 화면은 위반 단위 유지 (후속 과제).
